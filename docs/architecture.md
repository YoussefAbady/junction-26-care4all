# Architecture

The Next.js App Router serves a landing page, the guided questionnaire (`/`) and a plain-language privacy page (`/privacy`). Only the language and text size are stored in browser local storage.

**Questionnaire engine** (`src/lib/intake`). Content lives in `content/*.ts` as typed, bilingual question definitions. `engine.ts` computes the live question flow from the answers so far (conditions only see answers to questions that are themselves shown, so a changed answer cannot leave a hidden one steering the interview), expands follow-up blocks for each option picked in a multi-choice question, and validates every answer by type, range and permission to say "not sure". `report.ts` derives scores, safety alerts and the summary. The same engine runs in the browser and on the server.

**Persistence.** The dedicated survey API validates each snapshot against the intake engine. A finished questionnaire must be complete and confirmed. PostgreSQL stores progress and revisions in ScreeningSurvey, separate from credentials and sessions. Compatible legacy answers prefill the new intake and the original snapshot remains archived. The account route retains a compatibility contract for the existing client.

PostgreSQL stores prototype accounts, scrypt password hashes, saved progress and hashed login tokens. Seven-day HTTP-only session cookies identify the account. Revision checks prevent stale edits from overwriting saved answers. The service worker caches only its public asset allowlist and the public content response. Health data stays out of logs, URLs, browser storage and caches.

**Content.** All educational content lives in PostgreSQL and is the same for everyone: the PWA's topics, articles, guides, sources and interface text, the backend's bilingual cancer catalog, and the passages chat answers quote. It has no dependency on patient data. A seed (`prisma/seed-data`, run by `npm run db:release`) loads it when the hash of the seed input changes and otherwise leaves the database alone, so edits made in the database survive. `src/lib/content` reads it through a `ContentStore`: one implementation over PostgreSQL that caches by content version, and an in-memory one built from the seed for unit tests. `GET /api/content` serves the PWA's content with an ETag, `/api/cancers` and `/api/library` serve the catalog, and `ContentPassage` indexes every quotable passage for full-text retrieval. Emergency detection stays in code and needs neither the database nor a model. See [content in the database](content-database.md), and [backend integration](backend-api.md) for endpoint contracts.

**PWA container.** The care4all PWA is a separate project in `frontend/`: a Vite build served by unprivileged nginx. Browsers only reach nginx, which serves the app shell and forwards `/api/` to the backend, so the session cookie is same-origin and `APP_ORIGIN` is the PWA's own address. The service worker precaches the public shell and caches one API response, the public `GET /api/content`. It touches nothing else under `/api/`. The browser stores display preferences only. nginx logs paths without query strings. See [frontend](frontend.md).

Public deployment would require production identity and recovery, account deletion and retention policies, abuse protections, clinical review of the questionnaire, privacy review, and authorisation for use of the prototype branding.
